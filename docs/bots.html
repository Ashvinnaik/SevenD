What a Grok Bot PM actually does

A PM bot is not a chatbot you brainstorm with. It's a process manager — it takes the complete inputs for one SevenD phase and runs that phase to a decision.

Feed the Discovery PM a raw idea and market context, and it comes back with a prioritized backlog. Feed the Design PM an approved spec, and it comes back with a locked component registry and interface contracts. Every bot enforces the same phase gates the SevenD framework already enforces on humans and coding agents — no spec without a backlog item, no code without a completed design, no deploy without diagnostics passing.

Works at any level

The bots read whatever level you're on

A PM doesn't require Level 3+. It reads the complete input for its phase wherever that lives today — one markdown file, a phase folder, or a GitHub Issue — and produces the same gate-passing output either way.

1

Two files

Solo · weekend · prototype

Product.md carries Discovery + Definition + Design; Tech.md carries Development + Diagnostics + Deployment. Paste the relevant section into a PM as its complete input — expect a fast, low-ceremony pass.

2

Four files

Small team · real project

Same split, plus Architecture.md and Resources.md. Design PM and Development PM check against the shared component registry instead of guessing at names.

Recommended
3

Phase folders

Complex · weekly sprints

Each PM's natural home: its own phase INDEX.md + sprint file, plus reference/ (architecture, components, contracts, decisions). Document PM keeps STATUS.md as the board every other PM checks first.

4

GitHub-native

Team · CI/CD

Issues and Project fields stand in for backlog/spec/sprint files. A passing PR check is Diagnostics PM's complete input; Deployment PM's gate maps to that check passing before merge.

Directions

How to use a Grok PM bot

Same rule for all seven: complete inputs in, gate-passing output out. Here's the loop — starting with the one-time setup.

Setup · once
1

Set up shared context in Cursor

Grok Bots are built to run inside a Cursor project. Before opening any PM, the project needs its shared context in place — Project Scope, Roadmap, Vision, and Strategy — so every bot inherits the same foundation instead of re-deriving it per phase.

2

Assemble complete inputs

Fill in the SevenD file(s) for the phase you're starting — Product.md at Level 1, or the phase's INDEX + sprint file and reference/ docs at Level 3–4. A PM manages the process; it won't invent the backlog or the spec for you.

3

Open the matching PM

Click through to that phase's bot on x.ai. Paste or link your complete input — the approved output of the previous phase, plus any new context for this one.

4

Let it run the phase

The PM asks clarifying questions on any gap, then drives the phase to its canonical SevenD output — backlog, spec, blueprint, sprint plan, test verdict, or deploy plan.

5

Hand off, don't skip

Copy that output into the next phase's complete input and open the next PM. Document PM stays in the loop the whole time, syncing status across every phase.

Enforced automatically

The bots don't skip gates — even if you ask them to

Every PM inherits the same phase gates as the framework. Incomplete input means the bot pushes back and asks for it, instead of guessing.
